# Выбор и настройка мониторинга в системе

## Мотивация

За последний год бизнес «Александрита» столкнулся с системной деградацией качества сервиса при формально достаточных производственных мощностях. Рост количества заказов (B2C и через API партнёров) сопровождается:

- увеличением доли просроченных заказов;
- потерей крупных B2B-контрактов;
- ростом жалоб клиентов и партнёров;
- снижением производительности MES (в частности, дашборда операторов);
- отсутствием прозрачности по причинам задержек и «зависших» заказов.

Ключевая проблема — отсутствие наблюдаемости (observability) системы. Сейчас компания не может:

- быстро определить, на каком этапе жизненного цикла «застревают» заказы;
- отличить проблемы интеграции от проблем бизнес-процессов;
- оценить реальную пропускную способность MES, CRM и интеграций;
- аргументированно принимать решения о масштабировании, оптимизации или найме.

Внедрение мониторинга позволит:

- сократить время восстановления при инцидентах;
- выявить узкие места до того, как они станут бизнес-проблемами;
- обеспечить SLA/SLO для B2C и API-партнёров;
- дать бизнесу измеримую картину происходящего (основание для приоритетов);
- подготовить платформу к дальнейшему росту нагрузки.

Мониторинг в данном контексте — это не «техническая роскошь», а обязательное условие масштабируемости бизнеса.

---

## Выбор подхода к мониторингу

Система гетерогенна по нагрузке и ответственности компонентов, поэтому целесообразно использовать **комбинированный подход**:

- **RED (Rate, Errors, Duration)** — для внешних и внутренних API (онлайн-магазин, CRM, MES).
- **USE (Utilization, Saturation, Errors)** — для инфраструктуры и ресурсов (EC2, БД, очереди).
- **Четыре золотых сигнала** — как обобщающая модель для дашбордов уровня бизнеса.

Такой подход позволяет связать технические метрики с бизнес-эффектами (задержка заказов, недоступность API, потеря партнёров).

## Метрики и обоснование

### 1. RabbitMQ (интеграции CRM ↔ MES ↔ Shop)

**Number of dead-letter-exchange letters**  
- Зачем: индикатор потерянных или некорректно обработанных сообщений (прямая причина «пропавших» заказов).
- Ярлыки: queue, routing_key, source_service.

**Number of messages in flight**  
- Зачем: показывает накопление очередей и деградацию обработки.
- Ярлыки: queue, consumer_service.

### 2. API (Shop / CRM / MES) — RED

**Number of requests (RPS)**  
- Зачем: контроль нагрузки, корреляция с деградацией.
- Ярлыки: service, endpoint, method.

**Number of requests (RPS) per user**  
- Зачем: выявление аномального поведения партнёров API.
- Ярлыки: service, user_id, api_key.

**Response time (latency)**  
- Зачем: ключевой показатель UX и SLA.
- Ярлыки: service, endpoint, percentile (p50, p95, p99).

**Number of HTTP 500**  
- Зачем: явные ошибки, влияющие на заказы.
- Ярлыки: service, endpoint.

**Number of HTTP 200**  
- Зачем: базовая метрика успешной обработки (для расчёта error rate).
- Ярлыки: service.


### 3. MES (критически важный компонент)

**Number of simultaneous sessions**  
- Зачем: корреляция с медленной загрузкой дашборда.
- Ярлыки: role (operator/admin).

**Kb transferred / provided**  
- Зачем: выявление перегруженных представлений и неэффективных запросов.
- Ярлыки: endpoint.


### 4. Инфраструктура — USE

**CPU % (Shop / CRM / MES)**  
- Зачем: выявление необходимости горизонтального масштабирования.
- Ярлыки: service, instance_id.

**Memory Utilisation (services + DB)**  
- Зачем: контроль утечек памяти и OOM-рестартов.
- Ярлыки: service, db_instance.

**Number of DB connections**  
- Зачем: выявление connection pool starvation.
- Ярлыки: db_instance, service.

### 5. Хранилища

**Size of S3 storage**  
- Зачем: рост 3D-моделей напрямую влияет на стоимость и время расчётов.
- Ярлыки: bucket, model_type.

**Size of DB instances**  
- Зачем: контроль деградации запросов и индексации.
- Ярлыки: db_instance.


### 6. Дополнительные бизнес-метрики (рекомендуется добавить)

- Время нахождения заказа в каждом статусе.
- Количество заказов в статусе PRICE_CALCULATED > N минут.
- Количество заказов без перехода в MANUFACTURING_STARTED > SLA.
- Кол-во ошибок за промежуток времени (за день) расчёта стоимости в MES.

Эти метрики напрямую связывают мониторинг с потерями бизнеса.


## План действий (драфт ТЗ)

1. Выбрать стек мониторинга (Prometheus + Grafana как базовый вариант).
2. Развернуть или подключить ELK в облаке (скорее всего есть уже готовое решение).
3. Настроить сбор инфраструктурных метрик (node exporter, cloud metrics).
4. Инструментировать API (OpenTelemetry).
5. Подключить мониторинг RabbitMQ.
6. Добавить бизнес-метрики в MES и CRM.
7. Создать дашборды:
   - Технические (по сервисам).
   - Операционные (заказы, очереди).
   - Бизнес-дашборд для менеджмента.
8. Настроить алертинг (Zabbix): Slack / email / тикеты.
9. Обучить команду работе с дашбордами.

## Показатели насыщенности и реакции

**Зависшие сообщения в RabbitMQ > X (например, 1000)**  
- Действие: алерт + тикет DevOps, временное ограничение API-партнёров.

**Latency p95 MES API > 5 секунд**  
- Действие: алерт, запрет деплоя, анализ дашборда операторов.

**CPU MES > 80% в течение 10 минут**  
- Действие: автоскейлинг или добавление инстанса. Возможно алертинг - если это будет происходить часто, значит нам не хватает изначально заложенных рес-в.

**Заказы в PRICE_CALCULATED > 30 минут**  
- Действие: алерт бизнесу + технический разбор.

Такие реакции позволяют предотвратить повторение текущего кризиса, а не реагировать постфактум.
